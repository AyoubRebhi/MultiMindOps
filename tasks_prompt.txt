DEVSECOPS-AI-PLATFORM — PRE-TERRAFORM EXECUTION READINESS AUDIT
1. EXECUTIVE SUMMARY
The platform has a strong generation pipeline (Docker, Terraform, K8s, CICD), a real Docker build executor, an artifact approval model, JWT auth + sessions, and a project-centric data model with role gating on the new /api/projects/* routes. The deterministic backend_injector for backend.tf is well-conceived.

However, the platform is NOT ready to execute real Terraform. The blockers are not in the Terraform pipeline itself — they are in the execution substrate:

There is no TerraformExecutor. No code runs init / plan / apply / destroy. The validator runs terraform init -backend=false + validate in a temp dir only.
A dual governance model is live: project-scoped approvals on the Artifact table coexist with task-scoped Task.workflow_state JSON which is what the orchestrator and executor actually read. Approvals on the Artifact row do not gate execution.
Legacy routers (/workflow, /api/tasks, /api/execution, /api/tasks/{id}/artifacts, /api/corrector) require only authentication, not project membership. Any logged-in user who learns a task_id can run any phase, edit any artifact, trigger any Docker build, and (if added in the same pattern) trigger Terraform apply on any tenant's infrastructure.
Background work is asyncio.create_task fire-and-forget with no durable queue, no idempotency keys, no resume-after-restart. Terraform apply CANNOT live on this primitive.
github_token is persisted in plaintext inside Task.workflow_state JSONB. AWS credentials will go the same route unless the secret model changes first.
Verdict (full reasoning at the bottom): NOT READY. Three P0 blockers and a missing execution subsystem must land before any real terraform apply is wired up.

2. ARCHITECTURE STRENGTHS (don't break these)
Auth core is solid. backend/app/core/jwt.py + backend/app/services/core/auth_service.py + backend/app/models/session.py: access/refresh split, type-claim enforcement, server-side session rows with hashed jti, refresh rotation, dummy-verify on missing-user, lockout counter, constant-shape failure path. Genuinely production-grade.
backend_injector is correct. backend/app/services/terraform_generation/backend_injector.py — refuses to fall back to LLM, validates bucket/region/table format, keys state by task_id, hard-fails if TF_STATE_* envs are missing. The state-key convention tasks/{task_id}/terraform.tfstate keeps workflows isolated.
TerraformValidator subprocess isolation at terraform_validator.py:413-425: strips parent env to PATH+HOME, sets TF_IN_AUTOMATION=1, hard 90s timeout, temp-dir per call.
Artifact model is append-only. ArtifactVersion + ArtifactApproval give a real audit trail; the unique constraint (project_id, artifact_type, artifact_subtype) enforces "one current artifact per project".
Schema guard (backend/app/core/schema_guard.py) refuses to start on schema drift instead of silently 500-ing. Migrations are idempotent + ADD-COLUMN-only.
Project-centric authz (backend/app/core/authorization.py) factors require_project_contributor / require_project_approver correctly. Wherever it's applied, it works.
Plan-selection gate (workflow.py:223-275) prevents run-docker before select-plan.
3. CRITICAL BLOCKERS (P0 — fix BEFORE any real Terraform execution)
P0-1 — Legacy execution routes have no authorization
backend/app/api/routes/workflow.py:42, tasks.py:27-31, execution.py:577, artifact_edit.py:18, corrector.py

Every one of these declares dependencies=[Depends(get_current_user)] and nothing else. Tasks are not project-scoped at the model level (Task.project_id is nullable — see task.py:26). A logged-in DEVELOPER on Project A can:

POST /workflow/{any_task_id}/run-terraform
PATCH /api/tasks/{any_task_id}/artifacts — overwrite a peer's Dockerfile
POST /api/execution/docker/build/{any_task_id} — burn build budget
POST /api/corrector/{any_task_id}/reanalyze
If Terraform apply lands on the same router pattern, it will inherit this hole. The router comment on tasks.py:27 acknowledges it: "authentication alone is the gate today."

Fix order: (1) make Task.project_id NOT NULL, backfill via workflow; (2) require project_id in path on every task route, gate with require_project_role; (3) consolidate /workflow/* and /api/execution/* under /api/projects/{pid}/... or add a project-resolving dependency.

P0-2 — Approval is decorative, not enforcing
backend/app/services/core/workflow_orchestration_service.py:147-227

run_phase checks neither Artifact.approval_state nor ArtifactApproval history before running the next phase. Phase ordering is enforced solely by the string state["current_phase"]. A request_changes decision on the Docker artifact does not stop /workflow/{id}/run-terraform.

Worse: the executor reads artifacts from Task.workflow_state (the editable layer), while approvals are recorded on the Artifact row. The two stores are not bridged anywhere. A CLOUD_ARCHITECT approving artifact A does NOT mean the user-edited copy in workflow_state is approved — different content, different identity.

For Terraform apply this is fatal: a developer could PATCH the Terraform artifact bypassing the approver, then trigger apply on un-approved HCL.

Fix: introduce a single requires_approval=true precondition reading from ArtifactApproval (latest action == "approve" by a CLOUD_ARCHITECT) and reconcile Task.workflow_state ↔ Artifact so editing one updates the other (or kill the dual store).

P0-3 — Background execution is fire-and-forget
execution.py:747-760, corrector.py:166-169, projects.py:76-100

asyncio.create_task(...) and FastAPI BackgroundTasks:

Vanish on process restart. A terraform apply interrupted mid-flight leaves state-lock held in DynamoDB plus partially-created AWS resources, and the platform has no record of the in-flight job.
Have no per-(project, phase) mutex. Two clicks = two concurrent applys on the same state file.
Have no idempotency key. Retry-on-network-error doubles the spend.
Can't be cancelled. No terraform destroy mid-apply.
Docker survives this because builds are local and short. Real cloud apply does not.

Fix: introduce a real job runner (Celery/RQ/Arq, or even a single DB-backed jobs table polled by a worker process). One worker per project. Idempotency token in the request. Job heartbeat. Cancellation via signal forwarded to the terraform subprocess.

P0-4 — Secrets (github_token, future AWS creds) are persisted in plaintext JSONB
execution.py:710, orchestrator_agent.py:150, 885 — state["github_token"] is written into Task.workflow_state and read back.

A DB dump or any read of tasks.workflow_state is a wholesale credential leak. When AWS credentials enter the platform (env vars, IAM role config, TF_VAR_aws_secret_key etc.), they will follow the same path unless this is fixed first.

Fix: introduce an encrypted credentials table (project_credentials keyed by project_id + scope, AES-256 at rest with a KMS-held key), never store credentials in workflow_state. Inject into the subprocess env at run time. Redact from any log line that approaches them (the existing LogStreamManager does not redact).

P0-5 — No TerraformExecutor
There is no equivalent of DockerExecutor for Terraform. The codebase ships:

generation pipeline (templates + LLM + corrector)
static validation (hcl2_parse, terraform validate, tfsec, checkov)
deterministic backend.tf
But nothing runs terraform init/plan/apply/destroy against AWS. The platform is not ready to execute Terraform because the executor doesn't exist yet — it's a green-field component that must be designed under the constraints of P0-1..P0-4.

4. HIGH-RISK FINDINGS (P1)
P1-1 — JWT_SECRET default is a warning, not a fatal
config.py:115 — JWT_SECRET = "dev-insecure-change-me". The validator logs a warning if APP_ENV != "development" but does not refuse to start. In a misconfigured prod deploy (APP_ENV not set), the default secret silently signs real tokens.

P1-2 — AUTH_ALLOW_DEV_FALLBACK is a single bool away from auth-bypass
security.py:118-121. If left true in any environment that exposes a port, the seeded dev user is returned to every unauthenticated request. Acceptable for dev — make startup refuse to come up if AUTH_ALLOW_DEV_FALLBACK and APP_ENV != "development".

P1-3 — Self-healing OWNER membership runs inside the authz dependency
authorization.py:99-115. A Depends(...) dependency performs a write to project_members. Two concurrent requests from the same owner race on the same INSERT — handled because of the unique constraint, but the dependency will throw on the loser. More importantly, mixing writes into an authz check muddies the audit trail (who created the membership?). Move self-heal to a startup migration or a deliberate /repair-membership admin endpoint.

P1-4 — Phase ordering uses a mutable string field
state["current_phase"] (in Task.workflow_state JSONB) is the only source of truth for phase ordering. A user with PATCH access (P0-1) can flip it. Even without that, the orchestrator updates it freely. There is no append-only phase log. A workflow event-sourced model (or at minimum an enum column + transition guard) is needed before Terraform apply, where "did the apply complete?" must be unforgeable.

P1-5 — backend.tf state-key isolation is per-task, not per-environment
backend_injector.py:67 — tasks/{task_id}/terraform.tfstate. Reasonable as a starting point, but:

A re-run of the same task overwrites the state object. There is no env=dev|staging|prod segregation. The same workflow promoted from dev → prod would step on its own state.
DynamoDB lock table is shared across tenants. Acceptable, but the IAM policy on it must grant only dynamodb:GetItem/PutItem/DeleteItem on LockID keys matching the project — not the whole table.
P1-6 — Validator skips silently when binaries are missing
terraform_validator.py:240-246, 297-299, 348-350. terraform, tfsec, checkov absent → skipped status. The orchestrator currently treats skipped as not-a-failure. For production, missing security scanners must block apply, not be silently waved through.

P1-7 — Frontend stores JWTs in localStorage
tokenStorage.ts:5-6. XSS = wholesale credential theft. Refresh tokens are particularly damaging — 14-day lifetime per config.py:119. Recommend httpOnly + SameSite=strict cookies for the refresh token (kept on a custom path /api/auth/refresh) and keeping only the short-lived access token in memory (not localStorage).

P1-8 — User CSRF surface
With cookie-based refresh you must add CSRF protection. With localStorage you don't, but you eat XSS risk. Either way: there is currently no CSRF middleware. Worth deciding deliberately, not by omission.

P1-9 — CORS allow_credentials=true with broad allow_methods/headers
app_factory.py:133-139 — fine in dev (allowlists only localhost:3000) but make sure the production origin list is exhaustive and there is no * wildcard once credentials are enabled.

5. MEDIUM-RISK FINDINGS (P2)
P2-1 — User.is_active is a string column ("true"/"false")
user.py:24. email_verified and account_status use the same pattern. SQL-level queries like WHERE is_active = TRUE will silently miss rows. Use proper boolean columns. The model fixes this in Python with is_active_bool but storage shouldn't carry the legacy stringly-typed schema.

P2-2 — Workflow.phases_state is unstructured JSONB
workflow.py:36. Renames, typos, and out-of-band writers can all corrupt phase tracking. A separate workflow_phase_events table (append-only) would give a real audit trail and let you reconstruct phase history without trusting a mutable JSON blob.

P2-3 — Workflow current_phase and Task.workflow_state["current_phase"] are two independent truths
Phase string lives in both. There is no transaction guarantee they agree. The execution router reads from workflow_state; the project router reads from Workflow.current_phase. Drift will happen.

P2-4 — User.email_verified is checked nowhere
The column exists but auth_service.py:165-167 only checks is_active_bool and account_status. A user who hasn't verified email can still log in. Either enforce or drop the column.

P2-5 — ProjectMember.role carries no enforcement at the DB layer
String column, no check constraint. A direct UPDATE to role = 'GOD' would not be rejected by the DB and require_project_role would silently 403. Use CHECK (role IN (...)).

P2-6 — DockerExecutor 40-minute timeout
docker_executor.py:39-40. Large terraform applies (RDS provision, EKS) routinely exceed 40 minutes. The next executor needs a configurable timeout per phase and a heartbeat-based abort, not a hard wall clock.

P2-7 — ALWAYS_ALLOWED = {OWNER, ADMIN} ignores ADMIN-doesn't-exist-yet
authorization.py:39, 60-63. require_role("ADMIN") is a no-op since users have no global role column. Document or implement, don't leave it as a half-empty gate.

P2-8 — Logs persisted in Task.workflow_state["execution"]["docker"]["logs"] are unbounded
execution.py:434-443. Each retry appends. A long-running Terraform apply with verbose TF_LOG=DEBUG would blow this row to MBs and cause PG row-size pain.

P2-9 — No retention / cleanup for user_sessions
The model anticipates it (the index on expires_at is for "single DELETE WHERE"), but no cron, no startup sweep, no scheduled job is wired up. Sessions table grows monotonically.

P2-10 — Frontend Task.workflow_state is the source of truth, replicated client-side
The workflow page polls _phase_response(...) which embeds the full state. There is no event-stream + delta protocol — every poll re-sends everything. Scaling concern, not a blocker.

6. LOW-PRIORITY (P3)
Dead/legacy routes: /workflow/plan, /tasks/plan-preview, /tasks/generate overlap with /architecture-decision + project-centric flow. Pick one.
_TASK_ID_RE in backend_injector allows _ and - but BackendConfig.state_key could include them — fine, but make sure the operator's IAM policy Condition: { StringLike: { ... }} matches.
dist/ directory is checked in (frontend-React/dist/). Should be .gitignored.
GROQ_MODEL: str = "llama3-8b-8192" default doesn't match the GROQ_FALLBACK_MODEL capability tier — minor.
OPENAI_MODEL: str = "gpt-5.4-mini" — model name doesn't exist in the OpenAI catalog (typo for gpt-5-mini or gpt-4.1-mini?). Validate provider names at startup.

8. GOVERNANCE WEAKNESSES
Approval bypass: editing artifacts via PATCH /api/tasks/{id}/artifacts does not invalidate prior approvals. A CLOUD_ARCHITECT approves vN, a DEVELOPER edits to vN+1, executor runs vN+1 with vN's approval. No approval-cascade-on-edit.
Approval scope is single-artifact: an apply touches main.tf + variables.tf + outputs.tf + providers.tf. Approving one doesn't approve the set. Need a "release" / "apply candidate" concept that bundles + hashes the full Terraform module.
No "rejected" terminal state: rejecting an artifact only sets approval_state="rejected" — but the executor never reads that column.
Cross-project artifact leakage: artifacts are filtered by project_id in /api/projects/... routes. But the legacy /api/tasks/{id}/artifacts route does no project filtering — a peer task in any project responds.
Privilege escalation surface: the self-healing OWNER insert in require_project_role (authorization.py:99-115) writes to the membership table from a dependency that any GET hits. Edge case but worth tightening.
No "platform admin" gate: require_role("ADMIN") is a no-op. There is no way to forbid a developer from creating projects in production once registration is open.
9. SECURITY WEAKNESSES
Plaintext github_token in JSONB (P0-4).
JWTs in localStorage (P1-7).
JWT_SECRET default not fatal (P1-1).
Dev fallback not fatal in prod (P1-2).
No CSRF protection — fine with bearer-in-header, but a deliberate choice needs documenting.
_isolated_env in TerraformValidator is good; the (missing) executor must do the same and additionally remove any platform-set AWS_* envs except the freshly-injected role credentials.
Subprocess input not shell-quoted because subprocess.run(list[str]) is used (good), but the future executor must continue to pass argv-lists and not f-string into a shell.
validate_runtime_workspace (app_factory.py:21) is sound. The Terraform executor needs the same workspace-permissions sanity check.
CORS allow_methods=["*"], allow_headers=["*"], allow_credentials=True. Pin lists before prod.
No log-line redaction. AWS access keys, IAM secrets, GitHub tokens in terraform plan output will end up streamed verbatim over the WebSocket and persisted in workflow_state.execution.docker.logs.
10. OPERATIONAL WEAKNESSES
No durable job state — process restart loses in-flight work.
No "what is running right now?" admin view — Workflow.status="running" is the only signal, and rows are not heartbeated.
Unbounded log accumulation in Task.workflow_state row.
No session cleanup cron.
No request-id propagation through logs (audit trail across services is hand-pieced).
Build/apply timeouts are constants, not per-project policy.
Cost-control: no aws ce integration to refuse an apply whose estimated monthly cost exceeds a project budget. Cost estimation agent runs at plan time only.
No "kill switch" — an admin cannot stop all running applies without restarting the FastAPI process (and losing track of them, see P0-3).
11. SCALABILITY / MAINTAINABILITY
Workflow execution is single-process. A second uvicorn worker has no shared async-task state. The platform is effectively single-instance.
Two parallel models (Task.workflow_state JSON vs Artifact + Workflow) double maintenance cost and are the root cause of P0-2.
Workflow.phases_state and Task.workflow_state JSONB grow without bound.
The OrchestratorAgent is re-instantiated on every phase call (workflow_orchestration_service.py:165). Cheap for now, but cold-start of LLM clients and MCP connections will hurt at scale.
Frontend polls workflow state per-tick; no SSE/WebSocket fan-out from the workflow router.

13. RECOMMENDED FIX ORDER
Sequence is load-bearing — do not parallelize across these.

P0-1 Add project_id (NOT NULL) to Task, backfill, gate every legacy route with require_project_role. Kill the /tasks global list endpoint or scope it. Test: confirm a peer DEVELOPER on Project B gets 404 on Project A's task_id.
P0-4 Introduce encrypted project_credentials table; migrate github_token off workflow_state; add log redaction. Test: dump tasks table, confirm no secrets.
P0-2 Wire ArtifactApproval into a precondition for run_phase. Invalidate approvals on artifact edit (updated_at > approved_at → revert to pending_review). Reconcile Task.workflow_state ↔ Artifact (one writer).
P1-1, P1-2 Make JWT_SECRET default and AUTH_ALLOW_DEV_FALLBACK=true outside APP_ENV=development fatal at startup.
P0-3 Introduce a job runner (jobs table + worker process, or Arq/Celery) with idempotency keys and a per-(project, phase) advisory lock. Move Docker build onto it first as a smoke test.
P1-7 Move refresh token to httpOnly cookie; access token in memory only.
P0-5 Design TerraformExecutor on top of the new job runner with:
per-environment state key suffix
subprocess cancellation
heartbeat
"plan hash matches approved hash" guard before apply
severity-gated tfsec/checkov
destroy requiring typed project-name confirmation
AWS credentials injected via env only, never persisted
P1-4 Replace current_phase string with an append-only workflow_phase_events table.
P2-1, P2-5 Boolean columns; CHECK constraints on roles and statuses.
UX work (cancellation buttons, stale-plan warnings, destroy modal, audit timeline).
14. VERDICT
🛑 NOT READY for real Terraform execution.

The Terraform generation and validation pipeline is in good shape. The auth core is solid. The data model is mostly right.

But the execution substrate has three blockers (P0-1 authz holes, P0-2 ungated approvals, P0-3 ephemeral jobs) plus a credential-storage anti-pattern (P0-4), and the executor itself doesn't exist (P0-5). Running terraform apply on this platform today would mean:

any logged-in user can apply against any tenant's AWS account,
unapproved or edited HCL would apply identically to approved HCL,
a server restart mid-apply leaves DynamoDB locked and AWS half-provisioned with no record on the platform,
AWS credentials would land in the same plaintext JSONB column that already holds GitHub PATs.
These five P0s are pre-requisites. Land them in the order above, then build TerraformExecutor — don't build the executor first and retrofit governance around it. The retrofit will leak.
